Express工程化手册

分层架构、Zod 校验、错误处理、日志、ORM、测试与优雅关闭。

为什么需要工程化

一个 200 行的 app.js 在 demo 阶段没问题，但当需求增长到以下程度，系统将难以维护：

  • 10+ 路由文件集中在一个入口文件中
  • 数据库查询逻辑与路由处理耦合
  • 错误处理分散在各处的 try/catch 中
  • 缺少日志、缺少校验，线上问题只能依赖 console.log

工程化的核心目标：

目标 手段
职责分离 分层目录（route → controller → service）
数据安全 Zod 入参校验
错误可控 全局错误中间件 + AppError
可观测 Pino 结构化日志
数据持久化 Prisma ORM 封装
可测试 Supertest 集成测试
可靠运行 优雅关闭 + 重启策略

Prisma ORM 封装

什么是 Prisma

Prisma 是一个 Node.js ORM，通过 schema.prisma 文件定义数据模型，自动生成类型安全的客户端。

核心优势： 编译时类型安全 + 自动生成 SQL + 迁移管理。

Supertest 集成测试

为什么需要集成测试

单元测试 Service 能覆盖业务逻辑，但测不到：路由参数解析、中间件链、错误响应格式、状态码。集成测试补上这个缺口。

测试示例

测试要点

  • 用真实的 app 而不是 server，避免端口冲突
  • 测试成功路径 + 失败路径，确保错误格式一致
  • 数据库要能回滚，测试之间互不影响
  • supertest 自动处理请求的序列化和响应解析

优雅关闭服务

当进程收到终止信号时，需要：完成正在处理的请求 → 断开数据库连接 → 退出进程。暴力 kill 会导致请求中断、数据不一致。

实现

关键点

  • server.close() 停止接受新连接，等待现有请求完成
  • setTimeout 兜底防止关闭过程卡死
  • SIGTERM 是 Docker/K8s 的默认终止信号，必须处理
  • Prisma $disconnect() 释放连接池

常见问题

问题 原因 解决方案
Async error not caught Express 4.x 不捕获 async 路由异常 使用 asyncHandler 包装路由处理函数
400 请求返回空 body Zod safeParse 失败未处理 检查 validate 中间件是否正确返回错误响应
Cannot find module 路径错误 TypeScript 路径别名未配置 tsconfig.json 配置 paths，bun 原生支持 TypeScript 路径解析
Too many Prisma clients 开发报错 热重载导致重复创建 Client 使用 globalThis 单例模式
错误中间件不生效 注册顺序不对 确保 errorHandler 在所有路由和中间件之后
P2002 唯一约束报错 插入重复唯一字段数据 捕获 Prisma 错误码，返回 409
请求日志没有 requestId pino-http 未配置 genReqId 配置 genReqId 并在响应头返回 ID
优雅关闭时请求被中断 直接 process.exit() 使用 server.close() 等待请求完成
Query 参数类型错误 URL 参数都是字符串 使用 z.coerce.number() 自动转换类型
Supertest 测试端口冲突 直接启动 server 测试中使用 request(app) 而非请求真实端口
生产环境日志太多 日志级别设置过低 设置 LOG_LEVEL=warn，只记录警告和错误
TypeError: Cannot read property 空值 数据库查询返回 null 使用 Zod .nullable() 或 Service 层判空
